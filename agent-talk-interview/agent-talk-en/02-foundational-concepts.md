# 2. Foundational Concepts (theory)

This file explains **every term** that appears in the project, written for someone starting from scratch. Master this and you'll be confident against any "concept" question.

---

## 2.1. LLM (Large Language Model)

**What is an LLM?** An AI model trained on huge amounts of text to **predict the next token** in a sequence. That lets it write, answer questions, debate, etc. Examples: GPT (OpenAI), Llama (Meta), Gemini (Google).

**What is a token?** The small unit of text a model processes — it can be a word, part of a word, or punctuation. For example "conversation" may be split into several tokens. LLMs bill and limit by token count.

**In this project:** every agent line is generated by an LLM. The project code **does not invent the text itself**; it only:
1. Builds a "prompt" describing the character + context + history.
2. Sends the prompt to the LLM.
3. Receives and displays the reply.

### Key LLM parameters in the project

- **`temperature` (creativity)**: a number from 0 to ~2. Higher = more random/creative; lower = "safer", more consistent.
  - The project uses `0.9` for dialogue (needs creativity, variety).
  - Uses `0.2-0.3` for accuracy-critical tasks: picking the next speaker, summarizing, scoring, thinking up a search query.
- **`max_tokens`**: caps the reply length. The project uses `300` for dialogue, `40` for a search query (just keywords), `700` for scoring (needs long JSON).
- **`model`**: the specific model name, e.g. `llama-3.3-70b-versatile` (Groq).

## 2.2. API and "OpenAI-compatible"

An **API (Application Programming Interface)** is a "communication door" for one program to call another. Here we call the LLM provider's API over HTTP.

**What does "OpenAI-compatible" mean?** OpenAI defined a request/response format for chat (the `/chat/completions` endpoint, body with `model`, `messages`, `temperature`...). Many other providers (Groq, Gemini, OpenRouter) **deliberately mirror** that exact format.

➡️ **A huge benefit for the project:** you only write **one** LLM-calling function, then swap `base_url` + `api_key` + `model` to use any provider. That's why `config.py` lets you configure multiple "providers" while `llm.py` doesn't need to know who it's calling.

**The `messages` structure** (very important): a list of messages, each with a `role` and `content`:
- `role: "system"` → instructions/context (character description, the rules). The LLM treats this as the "ground rules".
- `role: "user"` → the "user's" words (in this project, the words of the **other** agents).
- `role: "assistant"` → the model's own words (in this project, the words of the **agent currently speaking**).

## 2.3. Streaming

**The problem:** the LLM takes a few seconds to produce a reply. If you wait for the whole paragraph before showing anything, the user stares at a blank screen → bad experience.

**The streaming solution:** the LLM sends back **small chunks** as soon as they're generated. The frontend displays them progressively → you see text "running out" like typing. Exactly the ChatGPT feel.

**How it works technically (SSE-like):** when you request with `stream: true`, the LLM server returns many lines like:
```
data: {"choices":[{"delta":{"content":"Hello"}}]}
data: {"choices":[{"delta":{"content":" there"}}]}
data: [DONE]
```
- Each line starts with `data:`.
- `delta.content` is the new piece of text.
- `[DONE]` signals the end.

This is close to **SSE (Server-Sent Events)** — a technique for a server to continuously push data to a client over a single open HTTP connection.

**In the project:**
- `llm.py` → `chat_stream` reads each line, extracts `delta.content`, `yield`s it.
- `main.py` → FastAPI's `StreamingResponse` wraps that generator and pushes it to the frontend.
- `app.js` → uses `response.body.getReader()` to read the stream and append progressively to the chat bubble.

## 2.4. Asynchronous programming (async / await)

**The problem:** calling the LLM API takes several seconds. If the code runs synchronously, it **blocks** until the result arrives, doing nothing else meanwhile → the server can't serve other requests.

**The async solution:** use `async def` and `await`. When it hits `await` (an I/O wait like a network call), the program **temporarily yields control** to handle other work, then resumes when the result is ready. This lets one server serve many users at once without many threads.

**Keywords to remember:**
- `async def foo()` → defines a "coroutine" (asynchronous function).
- `await something()` → wait for an async task to finish without blocking the whole program.
- `async for` → iterate over an async data stream (used to read streaming).
- `yield` inside `async def` → creates an **async generator** (produces data progressively, used for streaming).

**In the project:** every endpoint in `main.py` is `async def`. The LLM-calling functions (`chat`, `chat_stream`) and web search are async. `httpx.AsyncClient` is an async HTTP client.

## 2.5. FastAPI — the web framework

**What is FastAPI?** A Python framework for building web APIs, notable for:
- Built-in **async** support (runs on ASGI).
- **Automatic data validation** via Pydantic (define request types as classes).
- Auto-generated API docs.
- High performance.

**FastAPI concepts in the project:**
- **Route decorator**: `@app.post("/api/turn_stream")` binds a function to a URL path + HTTP method.
- **Pydantic model** (`BaseModel`): e.g. `class TurnRequest(BaseModel)` — FastAPI reads the JSON from the request, checks types, turns it into a Python object. Wrong type → automatic 422 error.
- **Response types**: `JSONResponse` (returns JSON), `StreamingResponse` (returns a stream), `FileResponse` (returns a file).
- **StaticFiles**: serves the frontend's static files (HTML/CSS/JS).

**ASGI vs WSGI:** ASGI (Asynchronous Server Gateway Interface) is the standard for **async** Python servers; WSGI is the older **synchronous** standard. FastAPI uses ASGI, run by **Uvicorn** (an ASGI server).

## 2.6. HTTP basics

- **Request/Response**: the client sends a request, the server returns a response.
- **Method**: `GET` (fetch data), `POST` (send data).
- **Status code**: `200` OK, `400` client error (bad request), `404` not found, `413` payload too large, `500` server error, `502` error from the upstream service.
- **Header**: extra info attached to requests/responses. The project uses a custom `X-Sources` header to send the list of web sources to the frontend.
- **Body**: the main content, here JSON.

## 2.7. Prompt Engineering

Since the code doesn't think, **the project's quality depends heavily on the prompt**. Prompt techniques used here:

1. **System prompt shapes the role**: "You are {name}. {personality}..." + reply rules (concise 2-4 sentences, full Vietnamese with diacritics, no action descriptions, don't play other characters).
2. **Structured context injection**: topic, hidden goal, memory, summary, debate phase — each is its own line/section in the system prompt.
3. **Clever role mapping**: the speaking agent's own words → `assistant`; others' words → `user` as "{name}: {content}". This makes the LLM "believe" it really is that character.
4. **Forcing output format**: when scoring, the prompt demands "return only valid JSON in the form {...}, no other text".
5. **Providing an exit**: when asking whether to search, "If no lookup is needed, reply exactly: NO".

## 2.8. Context management (context window)

The **context window** is the token limit the LLM can "see" in a single call. The longer the conversation, the more history → risk of **exceeding the limit** (and getting slower / costing more).

**The project's solution:**
- Keep the last `KEEP_RECENT = 8` turns verbatim.
- When total turns exceed `SUMMARY_WINDOW = 16`, **compress** the older turns into a short summary (calling `/api/summarize`), then send only: summary + the last 8 turns.

This is the **rolling summary / sliding window** technique — very common in real LLM chat products.

## 2.9. Other terms in the project

- **Persona**: the description of an agent's personality (the role).
- **Goal (hidden goal)**: a private agenda the LLM is told to pursue discreetly.
- **Orchestration**: arranging and controlling multiple LLM calls according to a logic (who speaks, when to summarize, when to score...). **This is the core of the project.**
- **localStorage**: a key-value store inside the browser; data persists after closing the tab.
- **TTS (Text-to-Speech)**: converting text to speech; uses the browser's `SpeechSynthesis`.
- **Path traversal**: a security flaw where an attacker uses a path like `../../etc/passwd` to read files outside the allowed folder. The project blocks it by only allowing alphanumeric session codes.
- **Mock (in tests)**: replacing a real function with a fake one so tests don't depend on external services.
